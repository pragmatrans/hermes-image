# Local patches applied at image build

Ці патчі накладаються на `/opt/hermes` **під час збірки образу** (`git apply` у Dockerfile).
`/opt/hermes` у нашому runtime read-only, тож іншого способу тримати патч у контейнері немає.

## Правила

- Один патч = один файл `NNNN-<slug>.patch`, unified diff з `-p1` (шляхи відносно `/opt/hermes`).
- У Dockerfile накладання йде двома кроками: спершу `git apply --check`, потім `git apply`.
  Якщо upstream переписав функцію — **білд падає**, а не тихо віддає тег без патчу.
- Після накладання — обовʼязкова перевірка: `python3 -c "import ast; ast.parse(...)"` плюс
  `grep` за унікальним рядком, щоб «патч застосувався, але не туди» теж валив білд.
- Факт наявності патчу видно з `/etc/hermes-tools.txt` (секція `== local patches ==`) — можна
  порівнювати два теги без копання в історію.
- Коли upstream випускає власний фікс — патч видаляється, а не «лишається на всяк випадок».

## Список

### 0001-cron-jobs-parse-retry.patch

`cron/jobs.py`: `_parse_jobs_file` робить до 4 спроб читання з паузами 150/300/450/600 мс, якщо
файл прочитався порожнім, і лише потім здається.

**Навіщо.** Стан cron може опинитись на ФС, де `rename` не гарантує атомарності (virtiofs у
Docker Desktop на macOS, будь-яка мережева ФС). Читач ловить 0-байтний `jobs.json`, а далі йде
каскад: auto-repair читає той самий файл → падає → жоден запис не відбувається (кожен запис
починається з читання) → кожен тік падає з `Cron tick error`, доки не перезапустити контейнер.
Реальний випадок: 17.11.2026, 88 хвилин тиші, 91 помилка поспіль.

**Статус тексту.** На маку причина вже усунена фізично (стан cron переїхав на ext4-том), на VPS
ext4 і так — тобто патч є **страховкою**, а не активним лікуванням. Якщо Slack/Python-парсер
колись отримає власний ретрай в upstream — патч прибрати.
